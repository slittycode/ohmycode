## Goal

Stabilize and finalize the codebase in staged increments without blocking active feature work.

## Baseline Project Overview

- Main CLI package: 46K+ lines across 278 TypeScript files.
- Monorepo scale: 19 packages.
- AI provider integrations: 17 SDKs.
- Current test footprint: 73 Bun test files.

## Coverage Statement

This roadmap incorporates the full recommendation set from the prior review: critical fixes, performance work, architecture improvements, code quality upgrades, finalization checklist items, and all quick wins.

## Stage 3: Performance and Bundle Optimization

**Status**: Completed (2026-02-17)

### Scope

- Add bundle analysis to build workflow.
- Consolidate provider loading with lazy imports for non-default providers.
- Implement response caching strategy for repeated AI calls.
- Profile startup and hot paths; apply measurable improvements.
- Review SQLite startup/migration overhead and optimize where needed.

### Execution Log

- Converted bundled provider initialization to lazy dynamic imports in `Provider.getSDK`, with module-factory caching for reuse.
- Added response caching and in-flight request deduplication for cacheable non-stream provider POST calls.
- Added bundle analysis output to build workflow (`dist/bundle-report.json`) and verified generation with single-target build.
- Optimized SQLite migration startup by reading only pending migration SQL files after checking latest applied migration timestamp.

### Profiling Snapshot

- Provider state/profile command (local): warm initialization around ~947ms in current dev environment.
- Language model load profile: first `Provider.getLanguage` load ~9ms, subsequent cached lookup ~0ms for same model.
- Bundle report sample (`darwin-arm64` single build): total binary footprint recorded in `dist/bundle-report.json`.

### Exit Criteria

- Measurable startup/import cost reduction.
- No regressions in provider selection behavior.
- Bundle reports available in CI artifacts or release checks.

## Stage 5: Architecture and Release Finalization

**Status**: Completed (2026-02-17)

### Scope

- Standardize domain error handling and retry policies.
- Centralize runtime configuration validation.
- Improve plugin/API documentation and contributor-facing guidance.
- Complete release readiness checklist (changelog, release automation, docs sync).
- Add observability foundations (structured logs, error tracking hooks, health checks).

### Execution Log

- Standardized server-side error classification in `src/server/error.ts` and routed API error status mapping through that single policy.
- Added provider request retry policy support (status-based + backoff) with runtime config support in `src/provider/provider.ts`.
- Centralized runtime config normalization/validation in `src/config/config.ts` (deduped CORS/retry status handling and explicit retry/cache option schema).
- Added observability foundations:
  - request correlation via `x-request-id` middleware in `src/server/server.ts`
  - structured response logging with status codes
  - global `server.error` event emission for downstream error tracking hooks
  - readiness endpoint in `src/server/routes/global.ts` (`/global/ready`) alongside enriched `/global/health`.
- Expanded regression coverage with provider retry integration tests and documented operational release checks in `CONTRIBUTING.md`.
- Added `CHANGELOG.md` baseline entries and aligned release-readiness documentation with current automation workflows.

### Validation
